## 3. 新发现问题清单（全部经人工二次确认）

### 3.1 P1 —— 建议尽快修复

#### E1. 拷贝失败后仍发射伪造的 Result.success（修复 `9348ccd` 引入的回归）
- 位置：`core/cache/CacheOpenManager.kt:113-121`
- 机制：通用 `catch (e: Throwable)` 只 `emit(Result.failure(e))` **没有 `return@flow`**，控制流经 finally 后落到 `:121` `emit(Result.success(CopyProgress(totalBytes, totalBytes)))`。任何拷贝中途 IO 失败（读失败/磁盘满/flush 失败）都会产生「failure 之后紧跟携带 `copied=total` 的假 success」矛盾序列。
- 影响：`ReaderFragment` 进度条先跳 100% 再弹错误；任何以「末值为终态」的收集方拿到错误终态。直接违背 P0-3 修复要建立的契约。
- 修复：`emit(Result.failure(e))` 后补 `return@flow`（一行）；并补失败路径单测（若当时已有，此缺陷当场暴露）。

#### E2. WebView file 白名单可被 `../` 与兄弟目录名绕过（P1-4 修复不完整）
- 位置：`core/reader/web/BlockingResourceWebViewClient.kt:74-79`
- 机制（人工确认）：`Uri.parse(url).path` **不做 dot-segment 规范化**，`file:///data/user/0/<pkg>/cache/app_cache/../../databases/history.db` 的 path 仍以缓存根开头 → `startsWith(root)` 放行；WebView（Chromium）实际加载时规范化 `..`，**可读取本应用任意私有文件**（含其它标签缓存、Room 数据库）。`%2e%2e`（解码后 `..`）同理。另外 `startsWith(root)` 缺尾分隔符，兄弟目录 `app_cacheX` 也匹配（`ReaderFragment.kt:401` 传入的 root 即无尾 `/`）。缓解因素：`javaScriptEnabled=false` 阻断脚本回传，但恶意 MHTML 可通过 `<iframe>/<img>/<link>` 把越界文件内容加载进阅读器 —— 恶意 MHTML 从 SMB/FTP 打开正是本应用核心威胁模型。
- 修复：比较前规范化 —— `File(path).canonicalPath.startsWith(File(root).canonicalPath + File.separator)`；补 `../`、`%2e%2e`、`app_cacheX` 三个回归测试（当前测试零覆盖此维度）。

#### E3. 在途拷贝的 cacheKey 不受淘汰保护（P0-5/P1-3 修复的并发窗口）
- 位置：`core/cache/CacheOpenManager.kt:83`、`core/cache/CacheEvictor.kt:45,51-55`、`core/reader/tab/DefaultReaderTabManager.kt:164`
- 机制（人工确认）：保护集 = `activeKeysProvider() + currentKey`，而 key 进入 `TabCacheRegistry` 的唯一时机是拷贝**完成后**的 `bind`。请求 A 持锁拷贝大文件期间（数秒~数分钟），请求 B 触发 `makeRoomFor` 时 A 的 key 既不在 activeKeys 也非 B 的 currentKey → A 的半成品目录被删 → A 完成后 `cacheFile.exists()` 为 false 报 "cache file not resolved"。这恰是本轮修复要闭合的并发打开场景，只保护了「触发淘汰的那一个 key」。
- 修复：`copyLocks` 已持有在途 key 的完整信息 —— 维护 `inFlightKeys` 集合（lock 前 add、finally remove）并入保护集；补「并发打开 + 淘汰压力」集成测试。

#### E4. 操作锁获取失败静默丢弃用户操作（B3 修复引入的 UX 回归）
- 位置：`app/src/main/java/html_reader/files/FilesRemoteController.kt:281,306,324`、`app/src/main/java/html_reader/FilesFragment.kt:499-501`
- 机制（人工确认）：上传/下载/SMB 变更纳入同一把独占锁后，长传输期间（无取消手段）本地重命名/删除/建目录/再次传输全部 `if (!tryAcquireOperationLock()) return` —— 对话框关闭后**什么都没发生**，无 toast、无状态栏提示、无排队。修复前本地操作与远程传输并发是 P1-1 缺陷，修复后走向了另一极端（静默拒绝）。
- 修复：锁失败时 `updateStatus(getString(R.string.files_status_operation_in_progress))`（新增资源）；可选：同 key 请求排队而非拒绝。

#### E5. 存量收藏明文凭据未做迁移清洗（P0-6 只修了增量）
- 位置：`core/database/AppDatabase.kt:36-52`（v2→3、v3→4 迁移均无 favorites 清洗）；全仓 `stripPassword` 调用点仅 FavoritesFragment:255 / JsonBackupManager / FilesErrorFormatter，无任何启动一次性清洗（grep 人工确认）
- 机制：v1.0.24 之前入库的 `ftp://user:pass@host/...` 收藏**至今仍以明文存于 Room**，违反 `CLAUDE.md 2.2.6`；打开该收藏时 `FilesNetworkOpenResolver.kt:54-56` 仍会从 URL 解出明文密码转存为网络配置。历史记录经链路追踪无此问题（key 为本地缓存路径）。
- 修复：启动时或随下次 DB 版本做幂等清洗回写（迁移 SQL 难以复刻 stripPassword 语义，建议应用层一次性任务 + 版本标记）。

#### E6. 收藏入库清洗未收口到仓库层（安全设计缺口）
- 位置：`core/data/repo/FavoritesRepository.kt:41-83`（`addFile/addDirectory` 原样入库）；未清洗的调用方：`TabsOverviewFragment.kt`（`path = tab.sourcePathRaw`）、`FilesFragmentEntryDialogs.kt`（addEntryToFavorites）
- 机制（人工确认）：P0-6 的要求是「入库前剥离」，正确收口位置是 Repository 写入口；实际实现是每个 UI 入口各自自觉调用。TabsOverview / EntryDialogs 当前不泄露是因为上游构建逻辑「恰好」不产生含密码路径（sourcePathRaw 为缓存路径 / FilesFavoritePathBuilder 只拼 username）—— **巧合安全而非设计安全**，任一上游语义变化即回归。
- 修复：`stripPassword` 下沉到 `FavoritesRepository.addFile/addDirectory` 与 `HistoryRepository.upsert` 写入口，UI 层调用成为冗余兜底。

### 3.3 附加发现

#### N1. Move/Copy 用例是无 UI 入口的休眠代码
`FileOpRequest.Move/Copy` 全仓**零构造点**（app 主源码仅构造 Rename/Delete/CreateFolder）。影响：
- P0-4 修复与 `MoveUseCaseTest` 目前是休眠代码，用户无法触发移动/复制功能；
- S1 的 SAF 死循环因此不可达（双保险：无入口 + SAF 目录转 LocalFile）；
- 与既有「领域用例未接线」债务（P2-2/C3 待决策）同域。建议：接线 Move/Copy UI 时先修 S1，或明确该能力的排期。

#### N2. resolver 宽匹配掩盖凭据语义
`FilesNetworkOpenResolver.kt:48-49` 仅按 protocol+host+port 匹配配置：收藏 URL 显式携带 `bob:pass`，但库中同 host 的 alice 配置被直接复用，bob 凭据被静默丢弃，用户无从得知连接用了哪个账户。建议匹配条件加入 username 并在复用时提示。
