### 2.1 S6：并发/生命周期，N03 未闭合

时序：A 已进入 IO 块、取 Mutex 前暂停；切 Web 取消 A；cleanup 未等 A，先 close 并完成；B 等 cleanup 后 open；A 恢复，空闲 Mutex 的 fast path 不检查取消，执行 closeInternal 并安装 A。generation 仅挡旧 UI，挡不住 controller 被写坏。仅切 Web 时也可在 close 后重开旧 A。

coroutines 1.8.1 `Mutex.kt` 第 50 行明确“不挂起时不检查取消”，165–168 行 `if (tryLock(owner)) return`。因此不能假设 withLock 自动消除该时序。

```kotlin
// Before: cancel 后丢失旧任务；cleanup 只等待上个 close
pdfLoadJob?.cancel()
pdfLoadJob = null
// After: 示意，必须由一次内容切换捕获且等待旧任务
val oldLoad = pdfLoadJob
val oldRender = pdfRenderJob
oldLoad?.cancel()
oldRender?.cancel()
val barrier = enqueueExit(previousExit, oldLoad, oldRender, controller)
// 下一次 open 必须等待 barrier，且再次检查内容代次。
```

`enqueueExit` 顺序为前次退出 → oldLoad.join → oldRender.join → close；任务图不能含当前 job 或未来 job。直接 PDF→PDF 和销毁也必须覆盖。open 锁内 closeInternal 前加 ensureActive 是防御补充，不替代 join。

### 2.2 S1：库接线/取消边界，T07 未闭合

SmbFile 没有将继承 URLConnection timeout 值传给传输。`SmbTransportImpl.java:494–495` 用 context config 的 conn/so，159–166 用 response。库默认连接/socket/response 为 35s/35s/30s，当前不是完全无超时，但新增 10s 设置没有兑现。

```kotlin
// Before
SmbFile(url, singletonWithCredentials).apply { connectTimeout = 10_000 }
// After: 示意，创建一次基础 context，保留现有安全配置及凭据语义
val properties = Properties().apply {
    setProperty("jcifs.smb.client.connTimeout", "10000")
    setProperty("jcifs.smb.client.soTimeout", "30000")
    setProperty("jcifs.smb.client.responseTimeout", "30000")
}
val baseContext = BaseContext(PropertyConfiguration(properties))
val authenticated = baseContext.withCredentials(authenticator)
```

不能每个文件都创建独立 transport pool；应用级基础 context 按现有策略共享，凭据 wrapper 按请求创建。保留协议/签名/匿名配置，不顺便全局降级安全策略。超时是单操作边界，不是上传总时长或 socket write 的严格墙钟保证。

### 2.3 S2：凭据防御，既有分页缺陷

101 行，首批 100 行读取后删除其中一行，下一次 OFFSET100 返回空，第101行保持明文。CAS 只保护读到的行；下次启动可能补迁移，不称永久丢失。

// Before: OFFSET += page.size

@Query("SELECT * FROM network_configs WHERE id > :afterId ORDER BY id LIMIT :limit")

### 2.4 S3：备份性能/协程，N02 部分遗漏

当前规划已是 O(n+e)，不再报 O(n²)。但 plan 在清表后事务内构建，同步校验/规划期间不观察取消；增加写事务持有时间和取消延迟，Room 回滚仍有效。

```kotlin
// Before: transaction { clear(); importFavorites() 内部 plan() }
// After
val prepared = prepareImport(bundle) // 验证、过滤和线性规划，可取消
transactionRunner.run {
    if (clearBeforeImport) clearEverything()
    restorePreparedImport(prepared) // 只执行写入和映射
}
```

校验分表拆分；规划循环传入 checkActive 或采用 suspend 规划方法。每节点或固定小批次检查，不借题升级序列化库。JSON 单次 decode 无法仅靠循环检查中断，如实保留这个有限输入 CPU 边界。

### 2.5 S4：失败告知，T07 原要求未闭合

远端 output 创建就可能创建/截断同名文件，不能以“写满第一块”作为起点。SMB 默认输出构造会 O_TRUNC/显式截断，FTP STOR 同样有副作用。普通异常只有通用文案，CE 路径无风险告知；不是新增写覆盖行为，也没有成功误报。

```kotlin
// Before: 直接打开远端 output，失败仅通用错误
// After: 进入可能有副作用阶段就登记；不把 CE 包成业务异常
attempt.markRemoteWriteMayHaveStarted()
remote.openOutput().use { copyCancellable(input, it) }
```

普通失败可以携带 PartialUpload(cause)；取消仍重抛原 CE，风险记录由独立结果状态保存。视图活跃时提示，销毁后不触碰旧 View；后续进入页面显示待确认风险。只保存不含密码的目标标识，不自动删除远端文件。不保证服务器事务回滚。

### 2.6 S5：目录项契约，新增低范围回归

`b.txt -> a.txt`，rename(a,"b.txt") 被 canonical 相等判为成功但未改名。仅支持 symlink 的文件系统有此反例，故低严重度；不能和跨进程 TOCTOU 混淆。

```kotlin
// Before
oldFile.canonicalFile == newFile.canonicalFile
// After: 同名目录项幂等；其他已存在目录项冲突
oldFile.name == toName
```

目标存在判断需要识别 dangling symlink，不能只用 File.exists 跟随链接。允许用 `Files.exists(path, NOFOLLOW_LINKS)` 做目录项存在检查；名称长度/保留字符和跨进程原子不覆盖仍是独立契约。

## 3. Agent 问题逐项答复

### Q1.1：Bitmap handoff

1. **可接受**，外层 finally 覆盖跨 dispatcher 返回被取消；不是因为 IO 内检查取消。
2. 当前 renderLocked 渲染失败先 recycle 后 throw，外层 `.also` 未执行，unclaimed 仍为空，不发生该路径双回收。成功交付清空责任，正常 UI 自行回收。
3. 零页 fallback 也是 renderLocked 正常返回，已经过 `.also` 登记，覆盖。
4. 同步 recycle 不挂起，不需要 NonCancellable。不要给整个渲染加 NonCancellable。
5. 仍需覆盖 page.close 抛错等“资源构造后、返回前”的异常；现有渲染 catch 不是整个 page.use 的全出口保证，测试/所有权辅助应将资源登记尽量提前。

### Q1.2：取消窗口测试

**选 A，不要求 B 大范围抽象 PdfRenderer。** 在 feature-reader 生效目录加小型 `PdfRenderHandoff` 或通用未交付资源 helper，接入真实 controller 的返回路径。测试用 Bitmap + 可控双 dispatcher。

```kotlin
// 最小结构示意，函数名可调整；生产必须调用它，不能只测一份复制逻辑。
suspend fun <T : Any> handoff(
    dispatcher: CoroutineDispatcher,
    produce: () -> T,
    release: (T) -> Unit
): T {
    var pending: T? = null
    try {
        val value = withContext(dispatcher) { produce().also { pending = it } }
        pending = null
        return value
    } finally {
        pending?.let(release)
    }
}
```

测试调度顺序：启动调用方 → 手动执行 IO 生产 → 暂不执行调用方 continuation → cancel → 执行调用方 → recycle 恰一次。另测正常不回收、生产抛错、零页等价分支。需要测试“产生后内部失败”时，可用在创建时登记资源的 owner，而不是加一个只返回成功值的 helper 就宣称全覆盖。原 page.use/Mutex 保留。

### Q1.3：close/open 链

1. **不够**，S6 时序成立。B 只等 close，不等 A load，不能证明旧 A 不迟到。
2. 直接 A→B 也不够：旧 A 已进入 IO、未取锁，取消后仍能取空闲锁并覆盖 B。
3. 当前 controller 每次 onViewCreated 创建，cleanup 传参捕获旧实例；没有发现闭包读取新字段导致混淆。仍需重建测试。
4. 没发现明确无限增长/死锁。排队的未完成任务有暂时成本，完成 Job 不应武断当永久链泄漏。可在主线程、确认 `pdfExitJob === completedJob` 后置空，不能 IO 直接写 Fragment 字段或误清新屏障。

### Q1.4：是否必须 actor

**不强制 actor。批准修正后的有序屏障方案**，条件是所有旧 load/render 的完成进入依赖图，直接 PDF 切换也覆盖；不只串 close。普通 Mutex/actor 改造都不是免测方案。

fake controller + barriers 必测：旧 open 在取锁前暂停；Web/空标签退出；B 等待；解除 A 后 close 再 B open；直接 A→B；销毁旧实例/重建新实例；旧 render 不写 UI/进度。不能只测两个 close 的调用顺序。

### Q1.5：完成状态

保持 **“需修改/复核未通过/设备待验”**。提交已经在 HEAD，不能称“待合入”暗示未进入分支。V01 修复和可控测试通过后标“代码复核通过/设备待验”；真实页、FD/内存趋势和旋转完成后才正式关闭整个 N03。

### Q2.1：阻塞 read 取消

1. 如果声明“关闭能解阻塞”，必须 latch + 外部取消测试；目前只能关闭协作式子项，保留阻塞 provider 待验。
2. 暂接受协作取消边界，**不强制 runInterruptible 或 invokeOnCompletion close**。SAF 没有通用 provider 超时保证，不能写“协作取消 + provider 超时已保证”。
3. 普通 invokeOnCompletion 要等 Job 完成，常常无法解救导致 Job 尚未完成的阻塞；不作为现成修法。更强机制需独立的拥有者、取消监听子协程和幂等 close，测试异常抑制/CE 优先；不依赖内部 onCancelling API。
4. runInterruptible 仅对真正响应 Thread.interrupt 的阻塞调用有效；不能推广到全部 ContentResolver/网络流。

### Q2.2：导出内存

没有违反“如实记录”的要求，注释已记录完整 ByteArray 峰值。**不阻塞 R5 协作取消验收**。后续可用 OutputStreamWriter 分段写 CharArray，保留跨块 surrogate pair/UTF-8 行为和取消检查；不变 JSON 格式。String/序列化仍是完整内存，不能宣传全流式。

### Q3.1：部分上传

**需要 UI 告知，不只写 MD**。可以 PartialUpload 处理普通失败，CE 另走风险状态而不包装。边界为“即将调用远端 output 创建”，它可能已经截断，即使返回抛错或写入 0 字节也有风险。活跃 UI 提示“可能已部分上传，请检查远端文件”，重进显示待确认记录；不自动删文件。

### Q3.2：SmbFile close

1. 当前默认 strictResourceLifecycle=false，stream.close 释放 file handle，不能直接称未关 SmbFile 导致永久连接泄漏。
2. stream.close 不等价 SmbFile.close：从既有 SmbFile 构造的 input 的 unsharedFile=false，不调用 file.close；output 也不关 file。strict 模式需显式释放 tree handle。
3. **推荐 SmbFile.use 外包 stream.use**，先流后文件，覆盖构造/拷贝失败。浏览 children 和目录操作也逐个关闭；不要为了关资源关闭共享 SingletonContext/pool。关闭 file 不承诺断开共享会话 socket。

### Q3.3：传输取消契约

保留“分块协作取消 + 实际客户端超时”，先修 S1。不强制 runInterruptible；它不能保证阻塞 socket write 的总 deadline。补 EOF、最后一块、打开连接前的 ensureActive，避免已取消任务开始新副作用。不将 readTimeout 解释成总时长或 writeTimeout；严格总期限需后续连接 abort 能力测试。

### Q3.4：rename 后取消

**可接受提交点竞态**：完整目标已原子替换，调用方仍可能收到取消；不能宣称“任何取消都不改目标”。不因取消回滚/删目标。把 rename 包 NonCancellable 也不能消除外层 withContext 返回取消，不保证成功信号。日志/结果如需区分，记录 commit point；本轮补前后取消测试和注释即可。

最小抽象放连接创建和资源 owner：内部 FTP connection factory / SMB resource factory，默认真实实现，测试可替换；不要使用 JVM 全局 URLStreamHandlerFactory。fake 验证两次都创建连接、同长度 A→B、超时参数、流关闭、异常传播。配置实际 charset（包括 Auto resolved 值）的测试应独立覆盖，不只 config.encoding。

执行方先提供设备/服务器验收脚本与清单；用户或项目维护者提供获准的测试环境。仅测试目录/账号，凭据在本机输入或环境变量，不写进 MD、日志和 Git。当前不要求用户先提供服务器才允许补 fake 测试。

### Q5.1：引用统一与回填屏障

1. **批准已有字段方案**，不变 schema v4。
2. AppSessionSourceStore 作为**只读 legacy**，不双写；保留键作为证据但新生产不能读取它 fallback。降级旧 APK 会继续读 stale prefs，不承诺跨版本降级一致性，发布说明明确。
3. FilesRuntime 只同步装配一个 binding service；`suspend ensureReady()` 由 service 持有 Mutex/幂等屏障。FilesStartupHandler、switch/observe、备份导入、网络配置编辑/删除均在入口 await。不能 FilesRuntime.ensure 持 JVM synchronized 做 suspend IO；Application 可预热，不能作为唯一保证。
4. 屏障失败必须传播并阻止后续操作，允许下一次重试；不能失败后标 ready，也不能 permanently failed Deferred 掩盖恢复。

### Q5.2：状态与 UI

- **批准** Local / Bound / Unresolved 三态，但 Bound 还要验证配置存在且协议匹配，正 ID 本身不足以称有效；decryptFailed 是 Bound 下的凭据不可用状态，禁止发送密文。
- LOCAL/null 且无 legacy key 才是本地。legacy 有 key 则迁移；无法取配置/协议标 UNKNOWN，保留路径，不根据 rootPath 推断服务器。
- SMB/FTP/UNKNOWN 失效：清空旧列表/选中项，取消旧加载，禁止浏览/上传/变更，显示“网络配置已失效，请重新选择”；保留卡片与当前位置，允许明确重绑。
- **全部入口必须切换**，包括 Deleter、Overview、Startup、SessionPlanner、More 删除/编辑、导入和本地复用。不得把失效网络当 unbound local。

### Q5.3：事务与模块放置

- **需要 SessionBindingRepository/service**：放 `core/data/repo`（core-data 既有映射生效），拥有同一个 AppDatabase、原始 suspend DAO 和一个 legacy snapshot 接口；不能 core-data 引用 app/feature-files。
- legacy 接口可放该层，AppSessionSourceStore 在 app 实现只读快照；FilesRuntime 注入。事务执行由 `AppDatabase.withTransaction`，app 不在每个页面重复手写组合规则。
- 网络会话 insert/source/binding 一次事务；配置 delete 与会话绑定置空一次事务。更新仅目标列，保留 currentPath/sort/time。当前会话/滚动 prefs 是派生 UI 状态，失败可恢复，不声称与 Room 一起原子。
- 回填事务内用 snapshot 对照当前 DAO，完成标记用 sourceType SMB/FTP/UNKNOWN；LOCAL/null 无 legacy 保持本地。不删除原键，不再双写。
- 备份层提供必需的 binding 导入协作者接口，由 Runtime 注入同一 service；它的方法参加**外层同一个 Room 事务**，不得启动提交后的独立修补。
- **不批量移除现有仓储 withContext**。Room 2.6.1 的生成 suspend DAO 经 `CoroutinesRoom.execute` 可回到事务 dispatcher；同步 DAO 或手工切 executor 才有不同约束。新跨表组合直接在 withTransaction 内调用 suspend DAO，测试证明。原注释“任何 withContext(IO) 都破坏事务”过于绝对，需按实际 DAO 修正。

### Q5.4：导入身份与追加

1. encoding 纳入，blank→Auto；Auto 大小写可 canonical 为 Auto，其他 Charset 别名只在验证后统一。
2. host 对 DNS 名用 Locale.ROOT 小写，无 DNS/network lookup；IP/特殊 host 用经过校验的规范，不凭 substring 猜。username **保留原大小写**，保持协议语义；不擅自 trim。
3. 同身份候选 >1 的受影响会话 Unresolved，不选第一条；其他唯一匹配会话不受影响。现有数据库唯一索引可能阻止部分重复，仍防御处理备份/未来数据，不放宽索引。
4. clear=false 保留存在且协议匹配的旧绑定，不抢绑新副本；无效旧绑定继续失效，不凭旧备份 ID 重绑。clear=true 清库前捕获旧配置身份，导入后唯一匹配新 ID，无匹配/多匹配置空引用并保留 source。
5. **必须保持 currentPath/sortOption/lastAccess/name/rootPath**；只改绑定列。配置身份恢复不等于密码恢复，空密码仍需重新认证提示。

### Q6.1：测试重载

**暂接受** @VisibleForTesting，无需为一次 CAS 验证引入完整 cipher 架构。加明确 KDoc，生产只调用无参方法，并检索调用点验证；注解不是访问控制/安全边界，不能说它阻止生产误用。以后将核心测试移入 core-data 后可改 internal/private helper。

### Q6.2：分页与 CAS

**改 keyset**，按 S2 方案；异常逐行继续不解决漏页。CAS0 不重试是正确的，避免追着用户编辑再次写。catch Exception 可继续，CE 单独重抛，不能 catch Throwable 吞 JVM Error。补“首批读后删除一行仍迁移末行”、分页顺序、CAS0 与取消测试。

### Q7.1：本地不覆盖范围

App 的 operationRunning 只管该 Fragment，不是所有 VFS 调用或跨进程锁。因此 **仅接受预检防主动覆盖，不称绝对 no-replace**。先修 S5/目标 dangling link。

不强制 ATOMIC_MOVE：它不等同 NO_REPLACE，目标存在行为可实现相关；NOFOLLOW_LINKS 用于目录项存在检查，不是 move 的不覆盖选项。更强策略必须针对 Android 文件系统验证 Files.move 默认非替换语义/平台 API，不能凭 API 名称作承诺。不顺便改变 Move/Copy 休眠能力。

### Q7.2：SMB 名称限制

现有字符拒绝作为最小安全规则可接受；**不无条件禁止所有 Unicode format 字符**，会伤害合法名称。不自动 trim 改名。尾随点/空格及保留设备名的 Windows 兼容规则按明确 SMB 策略拒绝并解释；不能宣传覆盖所有 NAS。

长度上限由协议/FS 定义（本地常按 UTF-8 字节，SMB 常按 UTF-16 单元），不引入全协议同一 `String.length <= 255`。共享校验器可接收策略，本轮不擅自收紧产品支持。

### Q7.3：SMB Conflict

**需要类型化 Conflict 和本地化映射**，不要 Unknown("Target already exists")。SMB 同名 rename 定义为已有源目录项时幂等，不发送 rename。客户端 exists 仍有竞态，服务端 renameTo 默认不替换应保留，并按 NT status 匹配冲突，不能只匹配英文字符串。

### Q8.1：planner API

public 暂接受：app 跨模块测试确实不能直接访问 core-domain internal。visitCount 标记诊断用途，不进入备份协议或 UI。无需为可见性重构模块；之后测试迁至 core-domain 时再收紧。公开 plan 需说明“输入已校验 ID 唯一且仅 FOLDER”，否则自己校验重复 ID，不能让外部重复/根与环输入无限排队。

### Q8.2：兼容语义

**选择兼容**：旧算法对不可达 pending 整体平铺挂根，后代不会重连。当前策略符合旧行为；有 id=null 的 FOLDER 根、FILE 父映射也正确。“重连子树更合理”是行为变化，另立需求，不在 N02 偷改。

### Q8.3：校验取消

**是 N02 未闭合项**，导入写循环不能覆盖前面的 validate/plan。按 S3 把准备工作移到事务前、校验分表和循环检查取消；保留 JSON decode 的局限，不称随时抢占 CPU。
